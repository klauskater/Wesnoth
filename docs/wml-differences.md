# Отличия WML порта от Battle for Wesnoth

WML порта похож на исходный WML внешней формой, но является отдельным языком.
Файл `.cfg` из Battle for Wesnoth нельзя переименовать в `.wml` и загрузить без
адаптации.

Полное описание поддерживаемого языка: [wml-reference.md](wml-reference.md).

## Краткая таблица

| Возможность | Battle for Wesnoth | Порт |
| --- | --- | --- |
| Теги `[tag]...[/tag]` | да | да, только отдельными строками |
| Вложенные и повторяющиеся теги | да | да |
| Повтор одного атрибута | допускается моделью config | ошибка |
| Несколько присваиваний `a,b=x,y` | да | нет; это одно имя `a,b` и одно значение |
| Склейка значений через `+` | да | нет |
| Удвоенная кавычка внутри строки | да | специальной обработки нет |
| Многострочное `<<...>>` | да | да, но `<<` и `>>` должны стоять отдельно |
| Переводимые строки `_ "text"` | да | нет |
| `#textdomain` | да | нет; строка считается комментарием |
| Макросы `#define` и `{MACRO}` | да | нет |
| Файловые `{includes}` | да | нет |
| Условный препроцессор | да | нет |
| Подстановка `$variable` | да | нет, `$` остаётся текстом |
| Формулы `$()` / WFL в значениях | да | нет |
| Дополнение `[+tag]` | да | нет семантики дополнения |
| Lua API Wesnoth / WML actions | да | нет; используется собственный API правил |
| Автоматическая локализация | да | нет |
| Схема стандартных тегов | большая стандартная схема | небольшая схема сценария этого порта |
| Terrain Graphics WML | макросный язык Wesnoth | отдельные компактные `[terrain_rule]` |

## 1. Препроцессора нет

Строка, начинающаяся с `#`, всегда комментарий. Поэтому не исполняются
`#define`, `#enddef`, `#ifdef`, `#ifndef`, `#ifhave`, `#ifnhave`, `#else`,
`#endif`, `#undef`, `#arg`, `#endarg` и другие директивы upstream.

Конструкции в фигурных скобках не раскрываются:

```wml
{campaigns/My_Campaign/scenarios}
{GENERIC_UNIT 2 "Orcish Grunt" 10 8}
```

В порте ресурсы перечисляются явно в `[resources]`, а повторяемая игровая
логика пишется в Lua.

## 2. Переменных и интерполяции WML нет

`$name`, `$unit.id`, `$array[0]` и `$()` не вычисляются. Например:

```wml
text="Gold: $gold"
```

даст буквальную строку `Gold: $gold`. Изменяемое состояние существует в Lua
через `context.state`; кампанийные значения используют префикс `campaign:`.
WML остаётся статическим входным деревом.

## 3. Строки проще

Исходный WML умеет составные значения, переводимые сегменты и специальное
экранирование кавычек. Порт лишь снимает одну пару внешних кавычек или читает
отдельный блок `<<...>>`.

Следующие upstream-конструкции переносить нельзя:

```wml
name= _ "Translated"
text="first" +
     "second"
text="He said ""hello"""
```

Для текста порта используйте одну строку в кавычках либо отдельный блок
`<<...>>`. Локализация пока является обязанностью адаптированных данных.

## 4. Атрибуты строже и одновременно менее типизированы

Повтор имени в одном теге — ошибка. Нет upstream-семантики выбора последнего
значения и нет параллельного присваивания через запятые.

Парсер сначала создаёт строки, а адаптер затем автоматически превращает любую
строку формата `i64` в integer. Кавычки не сохраняют строковый тип:

```wml
# Несмотря на кавычки, в Lua это integer, а не string.
id="123"
```

`yes` и `no` остаются строками. Это не общий тип boolean.

## 5. Модель дочерних тегов при передаче в Lua отличается

Внутреннее Rust-дерево сохраняет полный порядок детей. Универсальное Lua-
представление группирует их в `__children` по имени:

```lua
node.__children.attack[1]
node.__children.attack[2]
```

Порядок двух `[attack]` сохраняется, но чередование `[attack]`, `[ability]`,
`[attack]` превращается в две отдельные группы. Код правил не должен полагаться
на общий порядок тегов разных имён.

## 6. Стандартные игровые теги не поддерживаются автоматически

Совпадение имени не означает совпадение семантики. В частности, порт не имеет
универсального обработчика upstream-тегов `[event]`, `[message]`, `[filter]`,
`[set_variable]`, `[store_unit]`, `[modify_unit]`, `[terrain]`, `[sound]`,
`[music]`, `[endlevel]` и остальных WML actions/conditionals.

Аналоги нужных возможностей выражены небольшой схемой порта:

| Задача upstream | В порте |
| --- | --- |
| `[event] name=turn N` | `[turn_event] turn=N` |
| `[event]` + фильтр координат | `[location_event] x=... y=...` |
| событие атаки/смерти | `[attack_event]`, `[objective]`, `[achievement]` |
| `[message]` | ссылка `dialog=id` на отдельный `[dialog]` |
| `[endlevel]` | `[objective result=victory|defeat]` или финальная `[phase]` |
| `[unit]` внутри события | заранее объявленный `[unit reserve_group=...]` и `spawn_group` |
| `[set_variable]` между главами | `[campaign_variable]` либо Lua `context.state` |
| сценарные ветвления | `[phase]` и `[choice]` |

Неизвестные поля чаще всего молча сохраняются и игнорируются. Это удобно для
расширения Lua-правил, но опечатка не обязана стать ошибкой загрузки.

## 7. Lua — правила игры, а не Lua Wesnoth

В upstream WML может вызывать встроенные actions и Lua API игры. В порте
загруженные Lua-файлы возвращают собственную таблицу функций (`initialize`,
`snapshot`, `status`, `move`, `resolve`, `end_turn` и другие) и получают только
контролируемый `context` карты, объектов, состояния и RNG.

Нет совместимости с `wesnoth.*`, `wml.fire`, `wml.variables`, GUI, файловой
системой, временем и глобальным изменяемым состоянием upstream. Один вызов
правила транзакционен: при Lua-ошибке изменения и RNG откатываются.

## 8. Карты частично принимают исходные коды

Клетка карты может содержать код вроде `Gg`, `Gg^Fms`, `Kh` или `Ww`.
Геймплейный слой сводит его к одному из семи типов порта. Это не означает
полную поддержку terrain WML: неизвестный код по умолчанию становится
`grassland`, а графика определяется отдельной реализацией клиента.

Простые слова `grassland`, `forest`, `hills`, `water`, `castle`, `keep`,
`village` — собственные коды порта, отсутствующие как такая схема в upstream.

## 9. Terrain Graphics WML заменён компактным форматом

Upstream terrain graphics строится из большого набора препроцессорных макросов
и стандартных terrain-graphics тегов. Порт принимает только
`[terrain_rule]`, `[constraint]`, `[image]`, сам разворачивает до шести
поворотов и использует `@R0`…`@R5`.

Это намеренно узкая система композиции изображений, а не подмножество с
гарантированной совместимостью. Исходный terrain-graphics `.cfg` требуется
переписать вручную.

## 10. Практический порядок переноса сценария

1. Удалить препроцессор, includes, макросы и WML-переменные.
2. Явно перечислить карту, типы, диалоги и Lua-правила в `[resources]`.
3. Перенести стороны и стартовые юниты в схему из справочника.
4. Переписать события как `[objective]`, `[phase]`, `[choice]` и компактные
   одноразовые события; недостающую механику добавить в Lua.
5. Вынести `[message]` в файл `[dialog]`.
6. Проверить все типы местности, движения, защиты и сопротивления.
7. Запустить сценарий: часть ссылок и полей валидируется только во время
   соответствующего события.

Сравнивать результат следует по игровому поведению, а не по построчному
соответствию исходному WML.
