# План миграции к модульной архитектуре

Статус: в работе; M08 выполнен. План уточняет
[целевую структуру](README.md) и [проект протокола](protocol.md).
Реализация и текущие contracts продолжают описывать фактическое поведение.

Цель: сохранить работающую игру, передать всю игровую семантику Lua и перевести
клиент на команды и готовые представления. После каждого этапа приложение
собирается и предыдущие игровые возможности работают.

## Порядок и зависимости

Этап — проверяемый результат, который может потребовать нескольких небольших
коммитов. Перенос файлов и изменение поведения в одном коммите не смешиваются.
Следующий этап начинается после выполнения критериев предыдущего.
Сроки уточняются после исходных замеров; число файлов не является оценкой срока.

Это последовательность основной миграции, а не требование делать каждый этап
одним большим изменением. Внутренние шаги ниже выполняются отдельно.
Минимальные runtime/resources функции для require появляются уже в M01;
полное разделение хоста происходит в M06–M07. Выделение модулей не означает
преждевременную перепись их внутреннего устройства.

## Контракты до начала переноса

[Реестр контрактов](../../contracts/target/README.md) связывает каждый модуль
с API, гарантиями и потребителями. До переключения первого вызывающего уточнить
используемые игровые типы и физическое представление полей в соответствующем
контракте. Карточка модуля и комментарий исходника содержат ссылку на него.
Нельзя отмечать целевой контракт реализованным по одному существованию файла.

## Общие правила

- Ответственность, владелец состояния и граница зависимостей из
  [карточек](README.md#структура-модулей) копируются в заголовок каждого .rs/.lua.
  init.lua/mod.rs собирают модули, но не становятся новым монолитом.
- Сначала перенос существующего расчёта, затем отдельным изменением смена API
  или алгоритма. Формулы, баланс и дизайн игры в эту миграцию не входят.
- В каждый момент есть одна реализация правила. Временный фасад только делегирует.
  Старый код допускается как зафиксированный тестовый эталон вне runtime.
- Авторитетное состояние и RNG меняются только через транзакционный контекст.
  Кеш Lua можно удалить без изменения исхода игры.
- На этапе обновляются затронутые contracts, карточки модулей и проверки.
  Новые тесты проверяют границы и инварианты, а не повторяют структуру файлов.
- Рабочие изменения фиксируются небольшими коммитами. При неудаче откатывается
  незавершённая группа изменений; предыдущий работающий этап остаётся основой.
- Сетевой транспорт, ECS, глобальная шина событий и новый UI-фреймворк не нужны.
  Сохраняем один Rust crate, текущую библиотеку клиента и рабочие terrain-скрипты.

## M00. Зафиксировать исходную точку

**Работа**

1. Проверить рабочее дерево, сохранить перечень существующих изменений.
   Найти актуальных вызывающих через CodeGraph перед каждым переносом.
2. Запустить базовые проверки ниже, зафиксировать уже существующие ошибки.
3. Выбрать воспроизводимые сценарии для движения, боя/прогноза, найма,
   смены хода, fog/shroud, обязательного выбора и перехода кампании.
4. Записать seed, последовательность команд и ожидаемые ключевые результаты:
   позиции, HP, MP, золото, сторона, выборы и следующая глава.
5. В release-сборке измерить dispatch/query/present-предшественники, число
   переходов Rust ↔ Lua, объём преобразований и стоимость первой записи мира.
   Отдельно проверить повторный прогноз и AI на наиболее наполненном сценарии.

**Артефакт:** docs/migration-baseline.md с окружением, командами, входами,
результатами и измерениями. Создаётся при выполнении M00; сейчас его нет.

**Готово:** есть воспроизводимый эталон и список известных проблем.
Результаты тестов не объявляются успешными без фактического запуска.

## M01. Подключить настоящие Lua-модули

**Файлы:** engine/runtime и минимальный resources; scripts/game/init.lua;
загрузчик rule_source в game.rs; basic_combat.lua и simple_ai.lua.

**Работа**

1. Закрепить четыре entry-операции initialize/dispatch/interact/present;
   interact read-only и не вызывается при обычной пересборке present.
   Добавить host-controlled require: пути внутри пакета, кеш экспортов,
   понятная ошибка циклического импорта, одинаковый доступ с диска и embedded.
2. Модуль возвращает локальную таблицу. Убрать зависимость simple_ai от текстовой
   склейки и порядка объявления globals.
3. Добавить entry. Пока он делегирует старым правилам с прежними результатами.
4. Прекратить склейку Lua-файлов в одну строку исходников. Временные старые
   имена функций доступны через тонкий фасад.

**Проверки:** повторный импорт; недоступный/внешний путь; цикл импортов;
запуск тех же сценариев с прежними результатами.

**Готово:** правила вызывают друг друга внутри одной VM; код не перечитывается
при каждом действии. Новая модульность не меняет частоту вызовов правил.

## M02. Выделить нижние игровые правила

**Файлы:** scripts/game/rules/{units,sides,terrain,time}.lua.

**Работа**

1. sides: конфигурация сторон и союзов.
2. terrain: игровая трактовка местности; units: создание, traits, способности,

3. time: фазы суток и модификаторы; убрать дублирование формул у потребителей.
4. Заменить локальные helpers basic_combat импортами модулей.
   Внутренние вспомогательные функции остаются локальными.
5. Не переносить интерфейсные картинки в rules/time: они появятся в presentation.

**Проверки:** game_flow и соответствующие боевые случаи; одинаковое применение
союзов, traits, развития и времени суток.

**Готово:** эти правила имеют единственного владельца; нижние модули не
импортируют basic_combat, flow, AI или presentation.

## M03. Выделить движение, экономику, видимость и ходы

**Файлы:** rules/{movement,economy,visibility,turns}.lua; pathfinding bridge.

**Работа**

1. movement: достижимость, движение, MP, занятость и ZOC. Подготавливать веса
   и ограничения пакетом для Rust-поиска, без Lua callback на каждый гекс.
2. economy: захват деревень, доход, содержание, найм и recall.
3. visibility: обзор и скрытые объекты; изменение исследованности отделить

4. turns: начало/конец стороны, лечение, истечение статусов и смена суток.
5. Старый фасад временно сохраняет порядок общих вызовов; новые модули
   возвращают факты действий, не запускают UI или AI самостоятельно.

**Проверки:** pathfinding_bridge, game_flow; недопустимый найм без списания;
ZOC; лечение и доход ровно один раз; чтение видимости без изменения мира.

**Готово:** достигнутая клетка, стоимость найма и доступность действий
вычисляются одними правилами для выполнения и предпросмотра.

## M04. Перенести бой и прогноз в Lua

**Файлы:** rules/combat.lua, rules/forecast.lua; src/combat.rs;
боевые функции basic_combat.lua и fixtures.

**Работа**

1. Выделить prepare и чистый шаг боя: формулы, порядок ударов, specials,
   статусы, лечение от попадания. Выбор ветки попадания передаётся явно.
2. Реальное исполнение использует этот шаг и RNG транзакции.
3. Прогноз использует тот же шаг, разветвляя вероятности без игрового RNG.
4. Перенести impact/forecast из Rust. Сначала сохранить прежнюю семантику.
5. Сравнить распределения и реальные результаты, особенно slow, petrify,
   ответные удары и лечение. Старый kernel может временно служить только
   тестовым эталоном; после сверки убрать его и context.combat из runtime.
6. Повторить замеры M00. При замедлении сначала устранить повторные чтения,
   использовать подготовленные параметры и кеш. Если цель не достигнута,
   записать измерения и пересмотреть реализацию до закрытия этапа.

**Проверки:** combat_parity, game_flow; одинаковые детерминированные исходы;
сумма вероятностей с числовым допуском; RNG не меняется после прогноза;
профиль тяжёлого прогноза и повторного запроса.

**Готово:** клиент, AI и исполнение используют общие боевые расчёты Lua.
В production Rust отсутствуют правила slow/petrify/HP.
Ускоритель с игровыми понятиями нельзя оставлять под именем универсального ядра.

## M05. Собрать flow, сценарии, кампанию и AI

**Файлы:** game/{flow,scenario,campaign,ai}.lua; init.lua.

**Работа**

1. Перенести триггеры, цели, диалоги, обязательные выборы и результат в scenario.
2. Оформить campaign: каталог, вычисление переноса и выбор следующей главы.
   Rust-загрузчик пока может делегировать этим функциям.
3. Перенести оркестрацию из фасада в flow: общая проверка, действие, последствия,
   сценарные триггеры, обновление видимости. Задать детерминированный порядок.
4. scenario возвращает последующие действия в flow, не импортирует его.
   Цикл последствий ограничен; ошибка откатывает всю команду.
5. AI возвращает следующую команду и использует тот же dispatch.
   Автоматическое продолжение вызывается между завершёнными транзакциями,
   с ограниченным бюджетом. turns больше не содержит полный AI-цикл.
6. Важные pending-состояния держать в store; информационные панели не
   превращать в сценарное состояние.

**Проверки:** смерть → XP → развитие → цель сценария; обязательный выбор;
AI-команда через обычную валидацию; отсутствие рекурсивного цикла модулей;
воспроизведение последовательности событий.

**Готово:** basic_combat больше не владеет правилами и порядком действий.
Его оставшийся API только делегирует и удаляется в M11.
Никакая анимация не определяет продолжение правил игры.

## M06. Разделить ядро и закрепить транзакционные API

**Файлы:** src/engine/{mod,store,runtime,hex,pathfinding,value}.rs; lib.rs.

**Работа**

1. Перенести World/Object/RNG/Transaction в store, VM и bridge в runtime.
   Чистую геометрию, поиск и значения вынести по карточкам.
2. Исключить из Map::get игровую трактовку terrain; её предоставляет Lua.
3. Конкретизировать Value и Lua bridge по контракту engine/value:
   конечные дробные числа, различимые пустые list/record и явный null.
   Оформить read view и транзакцию с пакетными select/update.
   Read-only запрос не должен иметь доступ к записи и игровому RNG.
4. Добавить world_revision и ChangeSet только для committed данных;
   Lua domain events остаются отдельным результатом.
5. Исключить сохранённые Lua-ссылки на завершённую транзакцию:
   истёкший контекст отклоняет вызовы; Lua upvalues не обходят rollback.
6. Сначала сохранить существующий механизм хранения. Перейти к write set
   только при подтверждённой стоимости копирования мира; публичный API тот же.
7. Временные Rust re-export сохраняют сборку оставшихся потребителей.

**Проверки:** rollback мира и RNG после частичной записи; read-only запрет;
неподдерживаемый Lua-результат до commit; истёкший ctx; пакетные операции;
hex/pathfinding при прежних входных данных.

**Готово:** ядро разделено по ответственности, Lua имеет ограниченные права,
перенос файлов не создал несколько хранилищ мира.

## M07. Сделать загрузку и сохранения универсальными

**Файлы:** engine/{resources,data_format,persistence,session}.rs;
game/bootstrap.lua; game.rs/adventure.rs; embedded.rs/build.rs.

**Работа**

1. Ввести manifest с package id/version, entry, resource roots и версией протокола.
2. Перенести семантику сценария, unit types, races, traits и деревень из Rust
   в bootstrap. Rust предоставляет синтаксическое дерево и ресурсы.
3. Регистрировать произвольные неизменяемые каталоги без списка игровых ключей
   внутри Engine. Подключить уже выделенные scenario/campaign.
4. session управляет загрузкой, dispatch и продолжением автоматических действий.
   game.rs остаётся временным делегирующим адаптером.
5. persistence сохраняет универсальные записи, RNG и идентичность пакета;
   диалоги и перенос армии представлены игровыми данными store.
6. Restore не повторяет initialize с доходом/выбором traits/переносом армии:
   загрузить ресурсы, восстановить данные, проверить их Lua-валидатором.
7. Для старых сохранений по умолчанию повысить версию и вернуть ясную ошибку
   несовместимости. Конвертер старого формата не входит в текущий план;
   существующие файлы не перезаписывать.
8. Проверить комплектность embedded-ресурсов и запуск desktop/Android entry.

**Проверки:** одинаковый мир из disk/embedded; сохранение посреди выбора;
неповторяющийся carryover; следующий RNG после restore; неизвестная версия пакета.

**Готово:** Rust не знает схемы конкретного сценария, армии и кампании;
загрузка и сохранение идут через session.

## M08. Проверить новый поток на времени суток

**Файлы:** engine/protocol и session; client/{connection,view,ui};
presentation/{presenter,hud,map}.lua.

**Работа**

1. Зафиксировать точные типы сообщений из [проекта](protocol.md):
   CommandResult, Interaction, ViewSnapshot, ViewUpdate, UiNode, SceneItem.
2. Развести world_revision и view_revision; реализовать stale update → snapshot
   и повтор command_id → прежний результат в пределах сессии.
3. Реализовать минимальный набор UI для этой вертикали: контейнер, изображение,
   текст. Остальные компоненты добавлять при переносе их потребителей.
4. Lua выдаёт картинку, подпись, подсказку суток и tint карты. Клиент кеширует
   этот блок и не читает time_of_day.
5. Добавить пересборку после commit и при первом подключении.
   Ошибка present после commit не повторяет команду.
6. Остальные старые панели временно работают через адаптер Game; новый блок
   обновляется только новым путём. Два пути не вычисляют один и тот же блок.

**Проверки:** смена суток; начальный snapshot; изменение размеров окна;
устаревшее обновление; повтор команды; ошибка present с восстановлением;
ноль входов Lua на неизменных кадрах и движении камеры.

**Готово:** первая сквозная вертикаль работает через новый контракт.
Это контрольная точка для API: проблемы исправляются до переноса всех панелей.

Статус: **выполнено 2026-09-15**. Время суток публикуется отдельным UiNode-блоком
с label, image, tooltip, map tint и вариантом сцены; клиент читает только кеш View.
Проверены initial/update, resize, stale→snapshot, retry/dedup и восстановление после
ошибки present без повторного commit. Draw и движение камеры не обращаются к Lua.

## M09. Перевести игровой интерфейс и ввод

**Файлы:** client/{app,input,ui,view,connection}.rs;
presentation/{interaction,hud,presenter}.lua; screens/*.rs.

**Работа**

1. Панель юнита и список действий; затем найм/recall и прогноз боя.
2. Диалоги, развитие и сценарный выбор; затем каталог приключений и игровые меню.
3. Кнопки передают action, включая end_turn. Lua повторно проверяет допустимость.
4. Клик/hover поля интерпретирует interaction.lua. Камера, фокус и прокрутка
   остаются локальными. Hover объединяется только до смены целевого объекта/гекса.
5. Контекст выбора принадлежит наблюдателю; обязательные выборы остаются в мире.
6. После переноса каждой панели удалить её Rust-вычисления и старый query-вызов.
   Вся коммуникация клиента идёт через connection, а не напрямую в Lua.

**Проверки:** полный пользовательский путь выбрать → переместить → атаковать;
недопустимый action не меняет мир; выбранный юнит удалён; выбор восстановлен
после save/load; UI при resize; одинаковые действия мышью и клавиатурой.

**Готово:** клиент не читает HP/MP/gold и не решает, можно ли атаковать или нанять.
Изменение выбора обновляет UI без world commit. Панели и меню описывает пакет.

Статус: **в работе**. Через UiNode переведены end-turn, время суток, summary,
текст панели юнита, найм/recall и диалоги; UI-actions проходят через Interaction.
Остались бой, обязательные выборы и внешние меню, поэтому M09 ещё не отмечен.

## M10. Перевести карту, видимость и эффекты

**Файлы:** presentation/map.lua, effects.lua, terrain/*.lua;

Существующие проверки — основа; их имена могут обновляться вместе с API.

| Область | Текущая проверка |
|---|---|
| Игровой цикл, сценарии, кампания | tests/game_flow.rs |

| Клиентские сценарии | Встроенные тесты screens/game.rs; ручной запуск |

Базовая проверка на M00 и финальная на M12:

```powershell
cargo fmt --check
cargo test
cargo check --all-targets --features embedded-resources
```

Между ними запускать затронутые тесты, например:

```powershell
cargo test --test combat_parity
cargo test --test game_flow
cargo test --test pathfinding_bridge
```

Визуальная приёмка требует запуска клиента; успешная компиляция её не заменяет.
Android проверяется отдельной сборкой с фактически установленным toolchain.
Для составления этого плана игровые тесты не запускались.

## Итоговые критерии

- Все 40 карточек соотнесены с реализованными файлами; ответственность описана
  в самих модулях. Если граница изменена, решение обновлено явно.
- Rust-хост не знает правил юнитов, боя, суток, деревень и кампании.
- Клиент получает готовое представление и передаёт команды; локально хранит
  только восстанавливаемый view и техническое состояние интерфейса.
- Lua-команды атомарны; представление read-only; кеш не является источником истины.
- Ошибки и повторная доставка не дублируют действия и эффекты.
- Видимость соблюдается для каждого наблюдателя во всех выходных данных.
- Сохранения восстанавливают продолжение игры и RNG без повторной инициализации.
- Второй минимальный пакет работает без изменения движка и клиента.
- Измерения и платформенные проверки записаны; непроверенные пункты не отмечены
  завершёнными.
