# Контракт потока команд и представлений

Статус: целевой, не реализован. Редакция проекта: 1.

Обязательны [общие соглашения](common.md). Поставщик схемы —
[engine/protocol](modules/engine/protocol.md); оркестрация —
[engine/session](modules/engine/session.md).

## Граница клиента

Клиент знает типы визуальных элементов и сообщения, но не схему мира.
Ни World, ни unit snapshot не являются публичной моделью игрового интерфейса.
Встроенное подключение использует те же сообщения, без сериализации в JSON
между внутренними Rust-модулями. Это не требует внедрения сети.

```text
Command {
  command_id, expected_world_revision,
  action: string, payload: Value
}
Interaction {
  interaction_id, expected_view_revision,
  kind: activate | cell_click | hover | dismiss,
  target, payload
}
CommandResult {
  command_id, status: committed | rejected,
  world_revision, error?
}
ViewSnapshot {
  world_revision, view_revision, blocks
}
ViewUpdate {
  world_revision, base_view_revision, view_revision,
  replace_blocks, remove_ids, effects
}
```

Идентичность наблюдателя задаёт session/connection, а не доверенный payload.
action — имя публичной команды игры, а не имя произвольной Lua-функции.
Lua проверяет payload, принадлежность объектов, текущую фазу и ограничения.
Rust проверяет форму, ревизии, существование сессии и целостность транзакции.

world_revision увеличивается после изменения мира; view_revision отдельно для
каждого наблюдателя и увеличивается при изменении его представления, в том числе
при смене выбора без изменения мира. CommandResult и ViewUpdate связаны
world_revision, но ошибка построения представления не отменяет уже committed
команду. Клиент может запросить snapshot, не повторяя команду.
Повтор command_id в пределах сессии возвращает сохранённый результат без нового
commit; история дедупликации ограничивается сессией и не обещает сетевой exactly-once.

## Последовательность

1. Клиент обрабатывает локальные жесты камеры/фокуса самостоятельно.
2. Для игрового взаимодействия отправляет Interaction или action из UiNode.
3. session проверяет ревизию. interaction.lua интерпретирует игровое значение
   клика через отдельный entry.interact, обновляет только view context или возвращает Command.
   present не создаёт и не выполняет команды.
4. session запускает dispatch в одной транзакции. flow вызывает rules и
   обрабатывает их domain events/последствия в явном порядке до устойчивого
   состояния либо обязательного выбора. Ошибка откатывает записи и RNG.
5. После commit session получает ChangeSet и domain events. История событий
   не служит хранилищем мира: event sourcing не вводится.
6. present с read-only доступом строит видимые блоки и эффекты наблюдателя.
7. session отправляет результат команды и обновление; клиент применяет данные
   и рисует их из своего кеша до следующего обновления.

Domain events остаются внутри пакета и могут содержать игровые термины.
На клиент попадают только общие визуальные effects и готовые блоки.
Представление обязательного выбора вычисляется из store и воспроизводится
после восстановления, а не существует только как одноразовое событие.

## UI и сцена

UiNode содержит стабильный id, kind, общие layout/style поля, содержимое и
необязательное action. Начальный набор: Row, Column, Panel, Text, Image, Button,
List, Progress, Tooltip. Вложенные панели покрывают диалоги и модальные окна.
Клиент вычисляет пиксельную раскладку; Lua задаёт привязки, порядок и размеры.
Любые подписи, время суток, gold/HP и доступность действий вычисляет пакет.

SceneItem содержит стабильный id, asset, hex anchor/offset, слой, порядок,
tint, параметры кадров и необязательный hit id. Существующие договорённости
PlacedSprite сохраняются там, где они универсальны; названия семейств игры
не закрепляются типами в клиенте. Lua переводит family ordering в общие ключи.
Миникарта строится только из разрешённой наблюдателю сцены/слоя миникарты.

Фиксированная форма scene-блока редакции 1:

```text
{ schema: "scene", items: [{
  id, asset, frames?, frame_ms?, phase_ms?,
  anchor: {x,y}, offset?: [x,y], layer, order?, tint?: [r,g,b,a], hit_id?,
  clips?: [{x,y}], crop?: [x,y,width,height], masks?: [asset], opacity?
}] }
```

`frames` при наличии начинается с `asset`; `frame_ms > 0`, компоненты tint лежат
в 0..1, opacity — в 0..255, размеры crop положительны. Все asset/frame/mask ids
проверяются по immutable registry пакета. Начальные слои клиента: ground и world;
дополнительные слои вводятся редакцией контракта, а не скрытой эвристикой.

Начальная единица обновления — целый небольшой блок UI или участок сцены.
replace_blocks заменяет блок целиком, remove_ids удаляет верхнеуровневые блоки.
id каждого блока уникален; вложенные ids уникальны в пределах блока.
При замене блока удаляются все его прежние дочерние элементы.
Не проектируем произвольный diff каждого поля.
При неверной base_view_revision клиент запрашивает полный snapshot.
Snapshot задаёт текущее отображение и не воспроизводит старые effects.

Эффект имеет id = command_id + индекс + наблюдатель и общие параметры
анимации/звука. Для фильтрации исчезновения и боя можно использовать видимость
до и после команды; сырые сведения о скрытых объектах не передаются клиенту.
Анимация визуализирует уже принятый результат и может быть пропущена.
Пока идёт анимация, интерфейс может локально блокировать ввод, но допустимость
следующей команды всё равно проверяет Lua.

## Ограничение расходов Lua

- Постоянная VM и загруженные однажды модули.
- Обычно один dispatch и один present на наблюдателя для одной команды.
  Интерпретация игрового клика может добавить один вход; это не покадровая работа.
- Ноль входов в Lua на неизменный кадр, перемещение камеры или локальную раскладку.
- Hover отправляется при смене целевого гекса/объекта; можно объединять устаревшие
  hover до обработки, но нельзя терять игровые команды.
- select читает пакет объектов/полей; tx применяет пакет изменений.
  Нет экспорта всего мира как аргумента каждого вызова.
- Неизменяемые каталоги кешируются отдельно; вызов all без проекции в горячем
  цикле требует измерения. Нельзя считать копирование Rust/Lua нулевой стоимостью.
- Native pathfinding получает веса и ограничения целиком, без Lua callback
  для каждого узла. Подготовленные данные переиспользуются внутри операции.
- present сначала может перестраивать все малые UI-блоки после команды.
  ChangeSet позволяет явно выбрать крупные блоки; неизвестная зависимость
  означает перестройку. Автоматическое отслеживание чтения полей не требуется.
- Кеши учитывают ревизию, наблюдателя, параметры взаимодействия и версию ресурсов.
- Длинный AI обрабатывается ограниченными шагами между командами; flow сохраняет
  управление и возможность обязательного выбора. Лимит выполнения Lua прерывает
  транзакцию с rollback, а не оставляет частично применённый ход.

Отдельно измеряем число переходов границы, объём преобразованных данных,
время dispatch/present/forecast и копирование на первой записи транзакции.
Текущее Rc<World> копирует мир при первой записи; при подтверждённой стоимости
store реализует write set и commit изменённых записей. Это внутренняя оптимизация,
не причина менять контракт игры.

Rust combat kernel с правилами slow/petrify/healing не считается универсальным:
его семантика переносится в Lua. Оптимизация прогноза сначала использует общий
чистый combat step, кеш и пакетную работу. Native ускоритель обсуждается только
после измерений; он не должен фиксировать способности этой игры в движке.

## Уточнения идентичности и входов Lua

Внешние входы entry: initialize, dispatch, interact, present. Interact — read-only
интерпретация пользовательского ввода; повторное построение present не вызывает
interact повторно. Из результата interact session создаёт command с устойчивой
связью с interaction_id. Дубликат interaction_id не создаёт новую команду.
Тот же command_id с другим payload — conflict; проверка дубликата выполняется
до проверки ожидаемой ревизии, чтобы успешный retry не стал stale-командой.
Дедупликация ограничена жизнью сессии; её сброс требует новой session identity.

Snapshot/Update относятся к конкретной сессии и наблюдателю; connection не
применяет доставки прошлой сессии. Удаление и замена одного block id в одном
Update запрещены. Повторяющийся block id тоже ошибка. Применение пакета атомарно.
После Snapshot следующий Update ссылается на его view_revision.
UI target = block_id + node_id: id дочернего узла уникален только внутри блока.

Размеры, tint и вероятности допускают конечные числа; это требует расширения
нынешнего Value в M06, см. engine/value. Числовые диапазоны визуальных полей
проверяются до установки view. Точные поля layout/SceneItem должны быть
зафиксированы здесь в M08 до их использования клиентом.
